# Decision Log — Indian Fintech Data Science Case Studies

One log for all three cases. Each entry records the question, the options, the choice, and the
statistical and business reasoning. Entries are added in the order decisions were made.

- Case 1 = Juspay dynamic gateway routing (reference file, Case Study 1) → `01_payment_routing_success_rate.ipynb`
- Case 2 = Lendingkart MSME underwriting (reference file, Case Study 11) → `02_msme_credit_scoring.ipynb`
- Case 3 = Axis Bank omnichannel nudges (reference file, Case Study 22) → `03_nudge_campaign_ab_test.ipynb`

Global conventions (apply to every case unless an entry says otherwise):

- Random seed = 42 for every generator, split, bootstrap and model.
- Significance level α = 0.05 (two-sided) and power = 80%, unless a case entry changes them.
- Every dataset in this project that is labelled *synthetic* was generated by us. It is **not** company data.

## D-0-05: Seed 42 as the *root* seed, with independent child streams per random process

- Date: 2026-10-01
- Case: All (found in Case 1)
- Context / question: The brief says "seed = 42 everywhere". In the first Case 1 replay, both the outcome draws `u` and the rule router used `np.random.default_rng(42)`, so they received *identical* random numbers. Payments with high `u` (likely to fail) were systematically routed to PG_C/PG_D. That biased the rule-based baseline down by 1 pp (81.7% vs 82.7% observed) and doubled the apparent bandit uplift (+1.95 pp).
- Options considered: different literal seeds per process (breaks the "seed 42" rule); one shared generator consumed sequentially (order-fragile); `np.random.SeedSequence(42).spawn(k)`.
- Decision: Every independent random process is seeded from a child of `SeedSequence(42)`. Single-purpose generators (data generators, sklearn `random_state=42`) keep 42 directly.
- Why: Spawned streams are statistically independent and still fully reproducible from the single root seed 42.
- Assumption checks / evidence: After the fix, the replay's rule-based SR is 82.74%, matching the observed data (82.71%), and the uplift is +0.91 pp.
- Impact if wrong / mitigation: This was a silent bias that a sanity check (replay baseline vs observed SR) exposed. That check is now part of the workflow for every simulation.

# Case 1 — Payment routing (Juspay)

## D-1-01: Data source — synthetic transactions (no public data fits)

- Date: 2026-10-01
- Case: 1
- Context / question: We need transaction-level outcomes per gateway, with payment method, issuer bank and timestamp.
- Options considered: (1) public datasets (UCI ML Repository, data.gov.in, GitHub); (2) NPCI/RBI published statistics; (3) Juspay `decision-engine` repo; (4) Kaggle; (5) synthetic data.
- Decision: Synthetic data, about 4.2 lakh transactions over 30 days (1–30 Oct 2025).
- Why (statistical + business): No public dataset has gateway × bank × outcome rows. They are commercially sensitive. NPCI/RBI publish monthly aggregates only, with no gateway field. The Juspay repo has code, not data. Kaggle is excluded by the brief (no credentials). Simulation also gives a *digital twin* with known ground truth, which is the only way to evaluate a routing policy offline without real counterfactual outcomes.
- Assumption checks / evidence: Calibration achieved: rule-based SR ≈ 82.7% vs documented 82.60%. TS uplift ≈ +1 pp (≈ 1.2% relative) vs documented "up to 1.15%".
- Impact if wrong / mitigation: The exact ₹ figures are illustrative. The methods carry over unchanged to real logs (notebook Section 11).

## D-1-02: Synthetic parameter — success-rate level and gateway effects

- Date: 2026-10-01
- Case: 1
- Context / question: What baseline SR and gateway gaps should the generator use?
- Options considered: generic 90%+ SR; documented Juspay numbers.
- Decision: Method baselines UPI 85.5%, Card 79.5%, Netbanking 81.0%, Wallet 89.3%, plus gateway main effects (A +0.08, B +0.05, C 0, D −0.10 log-odds) and gateway × method / gateway × bank interactions of ±0.06–0.30 log-odds.
- Why: Rule-based SR must land near the documented **82.60%**. Overall gateway gaps of about 1 pp match the paper's toy example (80% vs 81%). Within-segment gaps of several pp echo "up to 7% in some card categories".
- Assumption checks / evidence: Clean data: overall SR 82.7%, with gateway SRs spanning about 6 pp (PG_D lowest).
- Impact if wrong / mitigation: Larger real interactions → bigger bandit gains, and vice versa. The γ-sensitivity and best/base/worst tables bracket this.

## D-1-03: Synthetic parameter — traffic mix and today's routing rules

- Date: 2026-10-01
- Case: 1
- Context / question: Method/bank shares and the fixed rules that produced the historical data.
- Options considered: uniform random routing; method-specific fixed splits.
- Decision: Method mix UPI 55% / Card 28% / NB 10% / Wallet 7%. Banks SBI 25, HDFC 22, ICICI 18, Axis 12, Kotak 8, Others 15 (%). Fixed per-method splits with cards pushed to the cheap PG_D (30%).
- Why: UPI dominance is typical of Indian e-commerce. Cost-driven rules that send cards to a cheaper, weaker processor mirror Cashfree Case Study 2. Method-dependent splits deliberately create **confounding** (Simpson's-paradox risk), which a professional analysis must detect.
- Assumption checks / evidence: The EDA traffic-mix table shows PG_D carries about twice the card share of other gateways.
- Impact if wrong / mitigation: Mantel–Haenszel and an adjusted logistic regression are reported alongside the raw comparison.

## D-1-04: Synthetic parameter — outage

- Date: 2026-10-01
- Case: 1
- Context / question: How should the documented outage be represented?
- Options considered: full blackout (SR = 0%); partial degradation.
- Decision: PG_B outage on 17 Oct 2025, 19:00–21:30 (2.5 h, evening peak), log-odds −2.5 (SR ≈ 35%), mostly authorisation-stage (timeout) failures, latency ×4.
- Why: The duration matches the documented "2.5-hour outage". Partial degradation is more realistic and harder to detect than a blackout. Peak-hour timing maximises business damage.
- Assumption checks / evidence: The p-chart flags the first outage window.
- Impact if wrong / mitigation: Milder outages are harder to detect. CUSUM/EWMA charts are proposed as a next step.

## D-1-05: Synthetic parameter — time of day and festive season

- Date: 2026-10-01
- Case: 1
- Context / question: What non-stationarity should be built in?
- Options considered: stationary SR; time-of-day plus festive effects.
- Decision: Hourly volume profile with lunch and late-evening peaks. SR −0.25 log-odds 00–05h (bank maintenance), −0.05 19–23h (load). Festive days 1–2 Oct and 18–21 Oct with volume ×1.35–1.9 and SR −0.12 log-odds (−0.22 for cards). Weekend volume ×1.1.
- Why: Indian banks schedule maintenance at night. Navratri/Diwali sales spike traffic and strain issuers. Routing and monitoring must cope with this.
- Assumption checks / evidence: EDA shows night SR about 3 pp lower and festive-day SR about 1 pp lower.
- Impact if wrong / mitigation: These are our assumptions (not documented). They mainly affect false-alarm rates, not the main conclusions.

## D-1-06: Synthetic parameter — failure stage split

- Date: 2026-10-01
- Case: 1
- Context / question: How should failures split between authentication and authorisation?
- Options considered: a single failure type; a stage split mirroring Cashfree.
- Decision: Share of failures at authentication: UPI 45%, Card 55%, NB 60%, Wallet 40%. **PG_D cards 78%**.
- Why: This mirrors the documented Cashfree finding that the weaker processor's gap is "due to higher authentication failures" while authorisation declines are about equal.
- Assumption checks / evidence: Chi-square of gateway × failure stage among failed cards (Section 7.3).
- Impact if wrong / mitigation: The size is our assumption. The flow-splitting recommendation must be validated on real logs.

## D-1-07: Synthetic parameter — amounts, latency, merchants

- Date: 2026-10-01
- Case: 1
- Context / question: Distributions of the non-outcome fields.
- Options considered: normal amounts; log-normal amounts with outliers.
- Decision: Log-normal amounts (medians ₹450 / 1,800 / 3,500 / 250 for UPI / Card / NB / Wallet, σ ≈ 1) with 0.05% bulk orders ×50. Small SR penalty for orders above ₹10k. Gateway latency medians 850 / 950 / 1,100 / 1,300 ms (×1.3 on failure). 120 merchants, Zipf(0.8) sizes, merchant SR effects ~ N(0, 0.15).
- Why: Indian e-commerce amounts are right-skewed. Large orders fail more often (limits, OTP). Latency is a natural guardrail.
- Assumption checks / evidence: EDA amount density (log scale) and latency boxplots.
- Impact if wrong / mitigation: GMV figures use the simulated amounts, so they scale with these medians.

## D-1-08: Data quality — injected defects and their treatment (outliers, missing values)

- Date: 2026-10-01
- Case: 1
- Context / question: What realistic defects should be built in, and how should each be treated?
- Options considered: drop vs impute vs flag, for each defect.
- Decision: Injected 0.6% duplicate `txn_id` rows (webhook replays, timestamp +1–30 s) as the **main defect**, plus 40 zero and 15 negative amounts, 25 epoch (1970-01-01) timestamps, 1% blank card networks and 1.5% blank latencies. Treatment: drop duplicates (keep first); drop amount ≤ 0; drop out-of-window timestamps. Label structural blanks "Not applicable" and true card-network blanks "Unknown". Leave latency NaN and exclude it only from latency stats. **Keep** amount outliers and flag them (`bulk_order`).
- Why: Webhook replays are the most common real SR-dashboard bug. They inflate n and make CIs too narrow. Zero/negative amounts are not customer payments. SR is binary, so amount outliers cannot distort it, and dropping genuine B2B orders would understate GMV.
- Assumption checks / evidence: SR per gateway changes by less than 0.05 pp after cleaning. About 2,500 phantom attempts removed.
- Impact if wrong / mitigation: Low. All treatments are logged in the notebook's DQ table.

## D-1-09: Confidence intervals — Wilson score interval

- Date: 2026-10-01
- Case: 1
- Context / question: Which CI for success rates?
- Options considered: Wald (normal); Clopper–Pearson (exact); Wilson; Agresti–Coull.
- Decision: Wilson for every SR interval.
- Why: Wald under-covers for small n or p near 0/1, which is exactly the case in short monitoring windows. Clopper–Pearson is overly conservative. Wilson has near-nominal coverage at any n.
- Assumption checks / evidence: At gateway level (n ≥ 69k) all methods agree to about 0.01 pp.
- Impact if wrong / mitigation: Negligible.

## D-1-10: Significance level, power and MDE

- Date: 2026-10-01
- Case: 1
- Context / question: What effect size should tests be powered for?
- Options considered: MDE 0.25 / 0.5 / 1.0 pp.
- Decision: α = 0.05 two-sided, power 80%, business MDE = **0.5 pp** SR.
- Why: 0.5 pp is about the documented dynamic-vs-rules gap (83.19 − 82.60 = 0.59 pp), so a test must see an effect that size. At this volume 0.5 pp ≈ 2,100 payments and ₹40+ lakh GMV a month, which is material. Two-sided, because a routing change could also hurt.
- Assumption checks / evidence: n ≈ **88,800 per arm** (1.78 lakh total ≈ 13 days of traffic at a 50/50 split). statsmodels `NormalIndPower`, the two-sample arcsine formula n = 2(z₀.₉₇₅ + z₀.₈)²/h², and the classic proportions formula all agree. A first draft omitted the factor 2 (that is the one-sample formula); this was caught by the cross-check and fixed. We recommend 14 days to cover two weekly cycles. Achieved power for 0.5 pp in the PG_C vs PG_B test: 84%.
- Impact if wrong / mitigation: A smaller MDE needs much more traffic (n ∝ 1/MDE²).

## D-1-11: Test choice — two-proportion Z-test (+ Mantel–Haenszel) for best vs second-best

- Date: 2026-10-01
- Case: 1
- Context / question: How should two gateways' SRs be compared?
- Options considered: two-proportion Z-test; 2×2 chi-square; Fisher's exact; logistic regression.
- Decision: Two-proportion Z-test with a Newcombe CI and Cohen's h, backed by a Mantel–Haenszel test stratified by payment method and an adjusted logistic regression.
- Why: For large n, Z² equals the 2×2 χ², but Z gives a direction and a CI for the gap, which managers need. It is also the documented Juspay method. Fisher's exact is unnecessary at n > 70k. MH is added because today's rules create method-mix confounding.
- Assumption checks / evidence: n·p and n·(1−p) are in the thousands. Groups are independent (one gateway per payment).
- Impact if wrong / mitigation: Ignoring confounding would overstate the PG_D gap. MH and the adjusted model are reported.

## D-1-12: Test choice — chi-square of independence + Cramér's V; LR test for the three-way question

- Date: 2026-10-01
- Case: 1
- Context / question: Are outcome and category (method, gateway, bank) associated, and does the gateway effect depend on the bank?
- Options considered: pairwise chi-square; log-linear model; logistic regression with interaction; Breslow–Day.
- Decision: Chi-square (no continuity correction, large n) for method × outcome, gateway × outcome and bank × outcome. Stratified chi-square per bank (Holm-corrected). A logistic-regression likelihood-ratio test for gateway × bank. Breslow–Day reported from the MH analysis. Gateway × failure stage for failed cards.
- Why: Chi-square handles more than 2 categories. Cramér's V gives a sample-size-free strength. The LR test is the cleanest formal test that "the best gateway depends on the bank".
- Assumption checks / evidence: Every table's minimum expected count is far above 5.
- Impact if wrong / mitigation: With n ≈ 4 lakh almost everything is "significant", so we stress Cramér's V and practical size.

## D-1-13: Multiple-testing correction — Holm–Bonferroni

- Date: 2026-10-01
- Case: 1
- Context / question: How should many simultaneous gateway/segment tests be controlled?
- Options considered: none; Bonferroni; Holm; Benjamini–Hochberg (FDR).
- Decision: Holm for every family (6 gateway pairs, 7 per-bank chi-squares, about 25 segment tests). Bonferroni is shown for contrast.
- Why: A false "winner" re-routes real money, so we control the family-wise error rate rather than FDR. Holm is uniformly more powerful than Bonferroni and valid under any dependence.
- Assumption checks / evidence: Segment winners are chosen on days 1–15 and tested on days 16–30, avoiding winner's-curse bias.
- Impact if wrong / mitigation: Holm is conservative and can miss small true effects. That is acceptable because the bandit handles residual differences adaptively.

## D-1-14: Decision model — discounted Thompson Sampling

- Date: 2026-10-01
- Case: 1
- Context / question: Which learning router should be compared against the fixed rules?
- Options considered: ε-greedy; UCB; Thompson Sampling; a Juspay-style PID controller; a contextual logistic bandit.
- Decision: Beta-Bernoulli Thompson Sampling per (method × bank) context, discounted, with 5-minute batched (delayed) feedback. Evaluated by replay on a digital twin with common random numbers, against the rules and an oracle.
- Why: TS is the simplest bandit that explores in proportion to uncertainty, which addresses Juspay's documented starvation problem. Discounting handles non-stationarity ("non-stationary bandit" in the paper). Batching mimics delayed feedback. The code is about 15 lines and transparent for business review.
- Assumption checks / evidence: TS beats the rules on every day of the replay.
- Impact if wrong / mitigation: A production version needs an exploration floor and cost-aware rewards (Section 11).

## D-1-15: Hyper-parameters fixed a priori — no tuning

- Date: 2026-10-01
- Case: 1
- Context / question: Should the bandit's discount factor or prior be tuned?
- Options considered: grid-search γ on the replay; fix γ a priori.
- Decision: γ = 0.99 per 5-minute batch (evidence half-life ≈ 5.7 h), prior Beta(8, 2), fixed before the replay. A 4-point γ table is shown only to demonstrate robustness.
- Why: The brief says no tuning. Tuning on the same replay that reports the uplift would overstate the gain.
- Assumption checks / evidence: Every γ in {0.98, 0.99, 0.995, 0.998} beats the rules.
- Impact if wrong / mitigation: γ trades reaction speed against noise. Re-evaluate on real traffic.

## D-1-16: Test choice — McNemar (paired) for policy comparison

- Date: 2026-10-01
- Case: 1
- Context / question: How should rule-based and TS outcomes on the same payments be compared?
- Options considered: two-proportion Z-test; McNemar; paired t-test on daily SR; bootstrap.
- Decision: McNemar (continuity-corrected) plus a paired-difference CI. An unpaired Z-test is reported as a conservative cross-check.
- Why: Common random numbers make outcomes paired. McNemar uses only discordant pairs and is the correct test. The Z-test ignores pairing, so it is conservative, and it is what a live 50/50 A/B test would use.
- Assumption checks / evidence: The discordant-pair counts are in the thousands, so the large-sample McNemar is valid.
- Impact if wrong / mitigation: None. Both tests agree.

## D-1-17: ₹ impact assumptions

- Date: 2026-10-01
- Case: 1
- Context / question: How should SR uplift be converted into ₹?
- Options considered: uplift × average ticket; the actual amounts of recovered payments.
- Decision: GMV recovered = actual ₹ of payments TS saved minus those it lost. Retry-recovery rate (failed payers who would have succeeded anyway on retry): base 50%, best 30%, worst 70%. Uplift: base = replay (+0.91 pp), best = upper paired 95% CI bound (+0.96 pp), **worst = Juspay's documented real-world gain of 0.59 pp** (83.19 − 82.60). The documented figure is used because the twin's CI reflects sampling noise only, not the risk that our simulated gateway differences are too generous. Also expressed per 1 crore monthly payments, and as orchestrator revenue at an illustrative 0.15% take rate.
- Why: Juspay's documented impact unit is "GMV recovered". Retry behaviour is not documented, so 50% is a neutral midpoint, and the scenario table shows its influence.
- Assumption checks / evidence: Section 9 shows every step.
- Impact if wrong / mitigation: A higher real retry rate → smaller net benefit. Validate with session-level retry data.

## D-2-02: Synthetic parameter — latent business quality and default calibration

- Date: 2026-10-01
- Case: 2
- Context / question: How do we make features predictive in a realistic way?
- Options considered: independent features with a hand-set logit; a shared latent "business quality" factor.
- Decision: A latent factor q ~ N(0,1), shifted by industry/tier/constitution/vintage, drives every feature *and* default (coefficient −0.65 on log-odds). Direct extra effects: bounces +0.22 each, declines +0.15, EMI/ADB > 1.5 +0.45, vintage < 2y +0.40, bureau −0.004/pt, NTC +0.30, YoY growth −0.010/pp, unregistered GST +0.35. Intercept −3.28.
- Why: Real cash-flow features are correlated because they all reflect business health. Calibrated to a pre-shock default rate of about 7% and a shock-period rate of about 10% (within the brief's 6–10% band).
- Assumption checks / evidence: DEV 6.7%, OOT 10.05%. A first calibration (q coefficient −0.95) made single-feature IVs unrealistically high (bureau 0.97, four features above 0.5). It was **recalibrated** so that the top IVs are 0.35–0.47 and model AUC ≈ 0.76, typical of real MSME scorecards.
- Impact if wrong / mitigation: Real signal strength may differ. All conclusions are framed as method-driven.

## D-4-04: Baseline method — trailing-14-day slot-of-day pooled SR, festive shift learnt on Dussehra, quasi-binomial z

- Date: 2026-10-13
- Case: 4
- Context / question: Razorpay's exact statistical method is "ND". What calendar-aware baseline should we use?
