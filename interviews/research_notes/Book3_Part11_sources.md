## Environment checks (run in Wave A, SQLite 3.45.1, Python 3.13 sqlite3, pandas 3.0.5; seeded random; no duckdb installed)
Schema used: orders(order_id INTEGER PRIMARY KEY, customer_id, order_date TEXT, status, amount, code TEXT) 200,000 rows; customers 20,000 rows.
Plan wording (EXPLAIN QUERY PLAN, 4th column):
- No index: `SCAN orders`. With index ix_cust(customer_id): `SEARCH orders USING INDEX ix_cust (customer_id=?)`; covering select: `SEARCH orders USING COVERING INDEX ix_cust (customer_id=?)`.
- customer_id+0=5 and strftime/substr/COALESCE/!= on a column: `SCAN orders`. customer_id=5 OR status='placed' (status unindexed): `SCAN orders`. customer_id=5 OR customer_id=7 and IN (5,7): one `SEARCH ... USING INDEX ix_cust (customer_id=?)`. customer_id=5 OR order_date='...' with both indexed: `MULTI-INDEX OR / INDEX 1 / INDEX 2`.
- WHERE customer_id=5 ORDER BY order_date: SEARCH plus `USE TEMP B-TREE FOR ORDER BY`. ORDER BY customer_id LIMIT 10: `SCAN orders USING INDEX ix_cust`, no sort. ORDER BY amount LIMIT 10: SCAN plus temp b-tree.
- SELECT DISTINCT customer_id (indexed): `SCAN orders USING COVERING INDEX ix_cust` (no temp b-tree). DISTINCT/GROUP BY on unindexed status: `USE TEMP B-TREE FOR DISTINCT` / `FOR GROUP BY`. GROUP BY customer_id: covering index scan.
- Range: `SEARCH orders USING INDEX ix_date (order_date>? AND order_date<?)`. Composite (status,order_date,customer_id): `(status=? AND order_date>?)`; with order of AND terms swapped the plan is the same. order_date>= only with (order_date) index: COVERING INDEX when only order_id selected.
- LIKE '2024-03%' on a plain TEXT index: `SCAN orders` (LIKE is case-insensitive, index BINARY). With `CREATE INDEX ... (order_date COLLATE NOCASE)`: `SEARCH ... (order_date>? AND order_date<?)`. LIKE '%03-05': SCAN. PRAGMA case_sensitive_like=ON was run only in the sequence (result not recorded as separate output): Wave B must run it and show the result-changing caveat.
- Type mismatch: with an INDEX on a TEXT column, `WHERE code=17` and `code='17'` both gave `SEARCH ... USING INDEX ix_code (code=?)`; INTEGER column compared with '5' or '42' literal also used the index; a column with no declared type compared with 42 used the index. Join a.k (TEXT) = b.k (INTEGER) used `SCAN a / SEARCH b USING INDEX ib (k=?)`; join on `b.k+0` or `b.k||''` flipped to `SCAN b / SEARCH a USING INDEX ia (k=?)` (still an index search, different outer table). So in SQLite a literal mismatch did NOT break the index in any case I tried; Wave B should not claim it does, and should hedge other engines.
- Joins: customers JOIN orders WHERE city='Pune' with index on orders(customer_id): `SCAN c / SEARCH o USING INDEX ix_cust (customer_id=?)`. Without that index (primary keys only): `SCAN o / SEARCH c USING INTEGER PRIMARY KEY (rowid=?)` (the planner scans orders and probes customers by PK; no automatic index). After ANALYZE with no index: `SCAN o / BLOOM FILTER ON c (customer_id=?) / SEARCH c USING INTEGER PRIMARY KEY (rowid=?)`. PRAGMA automatic_index=OFF made no difference in this schema (PK probe already available).
- Correlated subquery without an index on orders(customer_id): `SCAN c / CORRELATED SCALAR SUBQUERY 1 / SCAN o` (no automatic index built, with automatic_index ON, before and after ANALYZE). With index: `SEARCH o USING COVERING INDEX ix_cust (customer_id=?)`.
- Semi/anti joins with index on orders(customer_id): NOT IN: `SCAN customers / USING INDEX ix_cust FOR IN-OPERATOR`; NOT EXISTS: `SCAN c / CORRELATED SCALAR SUBQUERY 1 / SEARCH o USING COVERING INDEX ix_cust (customer_id=?)`; LEFT JOIN ... IS NULL: `SCAN c / SEARCH o USING COVERING INDEX ix_cust (customer_id=?) LEFT-JOIN`. IN (subquery with status filter): `SEARCH customers USING INTEGER PRIMARY KEY (rowid=?) / LIST SUBQUERY 1 / SEARCH orders USING COVERING INDEX ...`. EXISTS: CORRELATED SCALAR SUBQUERY. So SQLite turned IN into a PK probe from a list subquery and left EXISTS correlated.
- Partial index (customer_id) WHERE status='z' (rare value): used for `customer_id=5 AND status='z'` (`SEARCH ... USING INDEX ix_part (customer_id=?)`); `customer_id=5` alone: SCAN. For a partial index on o(cid) WHERE st='x': `st=?` bound parameter and `st='x'` both used it (as COVERING INDEX); `st IN ('x')` and `st!='y'` did NOT (SCAN).
- Expression index on substr(order_date,1,7): used as `(<expr>=?)` for the exact expression; substr(order_date,1,6) was not (SCAN, plan line not recorded: verify).
- Skip-scan: index ev(kind,ts) with kind of 2 values: `WHERE ts=777` was `SCAN ev` before ANALYZE and `SEARCH ev USING INDEX ix_ev (ANY(kind) AND ts=?)` after ANALYZE.
- WITHOUT ROWID: `SEARCH w USING PRIMARY KEY (a=? AND b=?)`; rowid table: `SEARCH r USING INDEX sqlite_autoindex_r_1 (a=? AND b=?)`; `WHERE b=1` on the WITHOUT ROWID table: SCAN.
- CTE: CTE used twice (UNION ALL): `COMPOUND QUERY / LEFT-MOST SUBQUERY / MATERIALIZE t ...`; AS NOT MATERIALIZED with outer filter showed CO-ROUTINE t; an inline GROUP BY subquery with outer filter: CO-ROUTINE plus SCAN. MATERIALIZED plan line not recorded: verify.
- Window with index (g, d DESC): `CO-ROUTINE ... SCAN s USING INDEX isg`; the unindexed variant shows `USE TEMP B-TREE FOR ORDER BY` after a CO-ROUTINE. Correlated top-3 forms: `CORRELATED LIST SUBQUERY 1` and `CORRELATED SCALAR SUBQUERY 1` with `SEARCH b USING COVERING INDEX isg (g=? AND d>?)`.
- Keyset with row value `(order_date,order_id)>(?,?)`: `SEARCH ... USING INDEX ix_od_id (order_date>?)` (only the first column is used as the search key; the row-value comparison is then re-checked). `WHERE order_id>100000 ORDER BY order_id`: `SEARCH orders USING INTEGER PRIMARY KEY (rowid>?)`.
- max(order_date) with index: `SEARCH ... USING COVERING INDEX`; count(*): `SCAN ... USING COVERING INDEX` of the smallest index.
- UNION ALL view over three monthly tables: `COMPOUND QUERY / LEFT-MOST SUBQUERY / SEARCH ev_1 ... UNION ALL SEARCH ev_2 ... UNION ALL SEARCH ev_3`: SQLite probes every branch (no pruning by value). Hedge for Wave B: it may differ with CHECK constraints (not tested).
- INDEXED BY ix_status with `WHERE customer_id=5` did NOT error: it printed `SCAN orders USING INDEX ix_status`. NOT INDEXED gives SCAN.
- sqlite_stat1 after ANALYZE: `('orders','ix_cust','200000 11')` (200,000 rows, about 11 rows per customer_id), `('customers', None, '20000')`; for ix_status with 3 values `'200000 50000'` (about 4 values at that moment; average per value), so the planner used 50,000 as the estimate for rare and common statuses alike. Plans for status='z' (0.1% of rows) and status='a' were identical (SEARCH USING INDEX ix_status).
- STALE EXPLAIN (important trap): Python's sqlite3 statement cache returns a stale plan: after DROP INDEX, re-running the identical `EXPLAIN QUERY PLAN ...` text still printed `SEARCH ... USING INDEX`, while the same text plus a trailing space printed `SCAN`. Wave B must use a fresh connection or vary the text (or c.execute(...) on a new Connection) after any CREATE/DROP INDEX or ANALYZE, and must verify every printed plan. (Cause assumed: EXPLAIN statements do not check the schema cookie; not documented-checked.)
VM steps (set_progress_handler(cb, 1) counts opcodes; deterministic across runs):
- 100,000-row orders: `WHERE customer_id=5` scan 300,025 to 300,026 steps (3 rows returned), with index 35 to 36, covering select 21; OFFSET 90000 LIMIT 20: 180,190; keyset `order_id>90000` LIMIT 20: 170.
- Insert of 100,000 rows via executemany: 1,100,006 steps with 0 secondary indexes, 1,700,006 with 1, 2,200,006 with 2, 2,800,006 with 3 (timings 196, 328, 459, 626 ms on this machine, machine-specific).
Timing noise: five repeats of the same indexed or scanned query varied by roughly 0.1 ms on a 2 ms scan; indexed lookups showed 0.0 to 0.02 ms (below timer resolution). Single timings on small data are noise: use VM steps, or report medians of repeats labelled machine-specific.
Write cost: file DB autocommit 2,000 inserts took 1,384 ms versus 2 ms in one transaction (machine-specific; disk sync dependent). Default journal_mode 'delete', synchronous 2; `PRAGMA journal_mode=WAL` returns 'wal'. compile_options show ENABLE_DBSTAT_VTAB (dbstat available), ENABLE_FTS5, DEFAULT_PAGE_SIZE=4096, MAX_VARIABLE_NUMBER=250000, DEFAULT_CACHE_SIZE=-2000, SECURE_DELETE.
Pages: 100,000-row table of (order_id, customer_id, d, amount): page_count 1025 at page_size 4096 (table 3,117,056 bytes plus index ix 1,069,056 bytes by dbstat). DELETE of half the rows left page_count at 1025 and freelist_count 2 (pages are half empty, not freed): VACUUM not run in Wave A.
Locking (file DB): default rollback journal: a reader inside BEGIN plus SELECT made the writer's INSERT fail with 'database is locked' (timeout 0.1); in WAL the writer succeeded and the reader still saw the old count (1). A reader during an uncommitted writer transaction could still read in both modes.
N+1: statement count via set_trace_callback was 101 for the loop (1 plus 100) and 1 for the grouped query.
pandas 3.0.5 (200,000 rows, machine-specific, one run each): vectorised a*b about 1 ms; apply(axis=1) about 1.6 s; list over iterrows about 4.3 s; over itertuples about 90 ms. memory_usage(deep=True): default str column 10,750,162 bytes vs category 200,215 bytes; int64 1,600,000 vs int8 200,000; float64 1,600,000 vs float32 800,000. groupby sort True vs False about 9 ms vs 9 ms; nlargest(10) 3 ms vs sort_values().head 11 ms; mask 2.3 ms vs query 4.4 ms (query slower at 200,000 rows); merge on a 4-row lookup 15 ms vs map 3.6 ms; .str.upper 19 ms vs map(str.upper) 15 ms vs apply lambda 18 ms (.str is not faster for plain upper). The default string dtype is `str` (not object). Copy-on-write is always on in pandas 3 (pd.options.mode.copy_on_write is deprecated and returns True with a Pandas4Warning): the chained-assignment demo and the pandas 3 warning text were NOT run, Wave B must run them.
