## Concept in plain language

### What is an algorithm?

An **algorithm** is a set of exact steps that, when followed in order, solves a problem or finishes a job. A cooking recipe is an algorithm. So is the way you reconcile a bank statement with your own records, if you write it down carefully.

A good algorithm has these properties:

| Property | Plain meaning | Quick test |
|---|---|---|
| **Clear** | Every step says exactly what to do | Could a new colleague follow it without asking you anything? |
| **Ordered** | The order of steps is stated | Does swapping two steps change the result? Then the order matters and must be written |
| **Finite** | It ends | Is there a point where it says STOP or runs out of items? |
| **Gives the same result for the same input** | No guessing, no "use your judgement" | Two people following it should reach the same answer |
| **Handles edge cases** | Works for empty, single, or odd inputs | What if the list is empty? What if two items tie? |

"Find the biggest sale of the week" is a **goal**, not an algorithm. It does not say *how*. An algorithm says: look at the first sale, then look at each next sale, keep the biggest seen so far, and so on.

### Pseudocode: steps written like code, but in plain English

**Pseudocode** ("pretend code") is a way to write steps that is more exact than a paragraph but is not tied to any real programming language. You can read it like a recipe. There is no "right" spelling; the point is to be clear. In this book we use these building blocks:

| Building block | How we write it | Meaning |
|---|---|---|
| **Variable** (a named box that holds a value) | `SET total TO 0` | Make a box called total and put 0 in it |
| **Input** | `GIVEN a list called sales` | What the procedure starts with |
| **Condition** (a yes/no test) | `IF number > largest THEN ... END IF` | Do the indented steps only if the test is true |
| **Two-way choice** | `IF ... THEN ... ELSE ... END IF` | One set of steps if true, another if false |
| **Loop over a list** | `FOR EACH item IN list ... END FOR` | Repeat the indented steps once for every item |
| **Loop with a test** | `WHILE test ... END WHILE` | Keep repeating while the test stays true |
| **Output** | `SHOW result` | Give the answer back |
| **Comment** | `NOTE: ...` | A reminder to the reader, not a step |

Indentation (steps moved to the right) shows which steps belong inside an IF or a loop.

### How to write an algorithm (a four-part routine)

1. **Say the input and the output.** What do I start with, and what must I end with?
2. **Do it by hand on a tiny example** and notice what you actually do.
3. **Write the steps in plain language**, one action per line.
4. **Turn them into pseudocode**, then **trace** it: walk through your steps on the tiny example, writing down the value of every variable after each step. If the trace gives the right answer, and also works on an empty list and a tie, you are done.

> **Why this matters for data work**
> Every query, formula or script you write is an algorithm in disguise. Analysts who can state the steps in plain words first make fewer mistakes and can explain their work in an interview or to a manager. Tracing a small example by hand is also the fastest way to find out why a calculation gives a surprising number.

## 5 solved examples

### Example 1: find the largest number in a list

**Input:** a list of daily sales, here 420, 385, 510, 465, 390. **Output:** the largest value.

**Plain-language steps:**
1. If the list is empty, say "no data" and stop.
2. Take the first number and call it the largest so far.
3. Look at each remaining number, one at a time.
4. If it is bigger than the largest so far, it becomes the new largest so far.
5. When there are no numbers left, the largest so far is the answer.

*Why step 2 is written that way:* "start with the largest number" would be circular (we do not know it yet). Taking the first number as the starting guess always works, because it is a real member of the list.

**Pseudocode:**

```text
GIVEN a list called daily_sales
IF daily_sales is empty THEN
    SHOW "no data"
    STOP
END IF

NOTE: the first value is our starting guess for the largest
SET largest_so_far TO the first value in daily_sales

FOR EACH sale IN the rest of daily_sales
    IF sale > largest_so_far THEN
        SET largest_so_far TO sale
    END IF
END FOR

SHOW largest_so_far
```

**Trace:**

| Look at | Bigger than largest so far? | largest_so_far after |
|---|---|---|
| (start) | | 420 |
| 385 | no | 420 |
| 510 | yes | 510 |
| 465 | no | 510 |
| 390 | no | 510 |

**Answer: 510.** *Why it works:* after every step, largest_so_far is the largest of everything looked at so far; so at the end it is the largest of all.

### Example 2: reconcile company records with a bank statement

**Input:** two lists of invoice numbers: company records 101, 102, 103, 104; bank statement 101, 103, 105. **Output:** invoices in the records but missing from the bank, and invoices at the bank but missing from the records. ("Reconcile" means compare two lists and explain every difference.)

**Plain-language steps:**
1. Make an empty list called "missing at bank" and another called "missing in records".
2. For each invoice in the company records, look for it in the bank statement. If it is not there, add it to "missing at bank".
3. For each invoice in the bank statement, look for it in the company records. If it is not there, add it to "missing in records".
4. Show both lists.

*Why two passes:* one pass finds only what is in list 1 but not list 2. Items that are only in list 2 would be missed, so we need the second pass the other way round.

**Pseudocode:**

```text
GIVEN a list called company_records
GIVEN a list called bank_statement
SET missing_at_bank TO an empty list
SET missing_in_records TO an empty list

NOTE: first pass, records checked against the bank
FOR EACH invoice IN company_records
    IF invoice is NOT in bank_statement THEN
        ADD invoice TO missing_at_bank
    END IF
END FOR

NOTE: second pass, the bank checked against the records
FOR EACH invoice IN bank_statement
    IF invoice is NOT in company_records THEN
        ADD invoice TO missing_in_records
    END IF
END FOR

SHOW missing_at_bank
SHOW missing_in_records
```

**Trace:** Pass 1: 101 is in the bank, 102 is not (add), 103 is in the bank, 104 is not (add). Pass 2: 101 is in the records, 103 is in the records, 105 is not (add).

**Answer:** missing at bank = 102, 104; missing in records = 105.

### Example 3: count how many values pass a test

**Input:** leave balances (days) of six employees: 12, 8, 15, 10, 22, 3. **Output:** how many have **more than** 10 days.

**Plain-language steps:**
1. Start a counter at 0.
2. Look at each balance.
3. If the balance is more than 10, add 1 to the counter.
4. At the end, the counter is the answer.

**Pseudocode:**

```text
GIVEN a list called leave_balances
SET employees_above_ten TO 0

FOR EACH balance IN leave_balances
    IF balance > 10 THEN
        SET employees_above_ten TO employees_above_ten + 1
    END IF
END FOR

SHOW employees_above_ten
```

**Trace:**

| balance | > 10? | counter after |
|---|---|---|
| (start) | | 0 |
| 12 | yes | 1 |
| 8 | no | 1 |
| 15 | yes | 2 |
| 10 | no (10 is not more than 10) | 2 |
| 22 | yes | 3 |
| 3 | no | 3 |

**Answer: 3.** *Why the 10 matters:* "more than 10" excludes 10. If the question had said "at least 10" the test would be `balance >= 10` and the answer would be 4. Precise words matter.

### Example 4: search a list and stop early

**Input:** a list of names: Asha, Ravi, Meena, Imran, Kavya, and a name to find. **Output:** the position of the first match, or "not found".

**Plain-language steps:**
1. Start at position 1.
2. If the name at this position is the one we want, show the position and stop.
3. Otherwise move to the next position.
4. If we pass the end of the list, show "not found".

*Why stop early:* once we have the match there is no reason to read on, which saves effort on a long list.

**Pseudocode:**

```text
GIVEN a list called names
GIVEN a text called name_to_find
SET position TO 1

WHILE position <= number of items in names
    IF the item at position in names = name_to_find THEN
        SHOW position
        STOP
    END IF
    SET position TO position + 1
END WHILE

SHOW "not found"
```

**Trace for "Imran":** position 1 (Asha) no, 2 (Ravi) no, 3 (Meena) no, 4 (Imran) yes, so show 4 and stop. **Answer: 4.**
**Trace for "Zoya":** positions 1 to 5 all fail; position becomes 6, which is more than 5 items, so the loop ends and we show "not found".

### Example 5: average that ignores blank entries

**Input:** scores 80, blank, 70, 90, blank. **Output:** the average of the scores that exist.

**Plain-language steps:**
1. Start a total at 0 and a count at 0.
2. For each entry, skip it if it is blank.
3. Otherwise add it to the total and add 1 to the count.
4. If the count is still 0, show "no data".
5. Otherwise divide the total by the count.

*Why count separately:* the number of entries (5) is not the number of real scores (3). Dividing by 5 would give 48, which is wrong for "the average of the scores that exist". Step 4 guards against dividing by zero.

**Pseudocode:**

```text
GIVEN a list called scores
SET total_of_scores TO 0
SET number_of_scores TO 0

FOR EACH entry IN scores
    IF entry is NOT blank THEN
        SET total_of_scores TO total_of_scores + entry
        SET number_of_scores TO number_of_scores + 1
    END IF
END FOR

IF number_of_scores = 0 THEN
    SHOW "no data"
ELSE
    SHOW total_of_scores / number_of_scores
END IF
```

**Trace:** 80 (total 80, count 1); blank (skip); 70 (total 150, count 2); 90 (total 240, count 3); blank (skip). Result: 240 / 3 = **80**.

## 2 real-life scenarios

*All numbers are illustrative (invented).*

### Scenario 1: flag employees with too many absences (HR, data)

An HR team wants a monthly list of employees who were absent **3 or more** days. Absence days: Anil 1, Bina 4, Chitra 3, Dev 0, Esha 5.

Plain steps: start an empty "flagged" list; for each employee, if absent days is 3 or more, add the name; at the end show the list.

```text
GIVEN a list of employees, each with absent_days
SET flagged_employees TO an empty list

FOR EACH employee IN the list
    IF employee.absent_days >= 3 THEN
        ADD employee.name TO flagged_employees
    END IF
END FOR

SHOW flagged_employees
```

Trace: Anil (1) no, Bina (4) add, Chitra (3) add (3 counts, because the rule says "3 or more"), Dev (0) no, Esha (5) add. **Flagged: Bina, Chitra, Esha (3 people).** Notice the edge case Chitra: the words "3 or more" versus "more than 3" would change the answer.

### Scenario 2: price after a discount rule (commerce)

A shop's rule: an order of 1,000 or more gets 10% off. A member also gets 50 off the final price. Four orders: (800, not a member), (1,200, not a member), (1,500, member), (900, member).

```text
GIVEN order_total and is_member
SET price_to_pay TO order_total

IF order_total >= 1000 THEN
    NOTE: 10% off means we pay 90% of the total
    SET price_to_pay TO order_total * 0.90
END IF

IF is_member THEN
    SET price_to_pay TO price_to_pay - 50
END IF

SHOW price_to_pay
```

| Order | Over 1,000? | Member? | Price to pay |
|---|---|---|---|
| 800, no | no | no | 800 |
| 1,200, no | yes: 1,080 | no | 1,080 |
| 1,500, yes | yes: 1,350 | yes: 1,350 minus 50 | 1,300 |
| 900, yes | no | yes: 900 minus 50 | 850 |

The **order of steps** matters: discounting first and then subtracting 50 is a different rule from subtracting 50 first and then discounting. The algorithm must say which.

## Mistake log

1. **Writing a goal instead of steps.** "Find the largest" says what, not how.
2. **Ignoring edge cases.** Empty lists, ties, blanks, and the word "at least" versus "more than" cause most wrong answers.
3. **Starting a variable at the wrong value.** Starting "largest so far" at 0 fails if all numbers are negative; starting a counter at 1 instead of 0 gives an answer one too high. Use the first real value for largest/smallest and 0 for totals and counts.
4. **Forgetting to update inside the loop** (or putting the update outside it), so the variable never changes or changes only once.
5. **Never tracing the steps.** An algorithm that looks right can fail on the very first test; a two-minute trace on a tiny example catches it.

## Recap

1. An algorithm is a clear, ordered, finite set of steps that gives the same answer for the same input.
2. Write the input and output first, do a tiny example by hand, then write plain steps, then pseudocode.
3. Pseudocode uses variables, IF conditions and FOR EACH or WHILE loops; its job is clarity, not correct spelling.
4. Check edge cases: empty input, ties, blanks, and exact wording like "at least" and "more than".
5. Trace your steps on a small example, writing down each variable after each step.
