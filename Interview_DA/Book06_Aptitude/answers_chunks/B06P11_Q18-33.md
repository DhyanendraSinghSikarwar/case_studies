### Q18 ⭐⭐ 🟢 Complete the conditional sentence correctly: "If the data ___ (be) clean, the dashboard ___ (load) faster." Name the conditional type, and give the correct form for a "real/probable" situation and for an "unreal/hypothetical" situation.

**Answer:** **Real/probable (first conditional): "is" and "will load". Unreal/hypothetical (second conditional): "were" and "would load".**
**Step-by-step working:**
1. Decide whether the situation is possible in the future (we may well clean the data) or imaginary/contrary to fact (the data is dirty now and we are only supposing).

**Explain simply:**
- A conditional sentence has an "if" part (the condition) and a result part.
- First conditional: a real possibility. Second conditional: a daydream or something unlikely or untrue now.
- Memory trick: "will" goes with "is" (present), "would" goes with "were" (past form).
- Third conditional (for completeness): If the data had been clean, the dashboard would have loaded faster (a past regret).

### Q19 ⭐⭐ 🟢 Which normal form removes partial dependency, and what do 1NF, 2NF and 3NF each require? Illustrate with the table orders(order_id, product_id, product_name, customer_name) where the key is (order_id, product_id).
**Asked at:** commonly asked (no company-specific report found); normalisation is a standard DBMS fundamentals item (DBMS presence in Accenture and Tiger Analytics tests is reported by prep sites and one institutional note, not confirmed).
**What the interviewer is checking:** Whether you can name the normal forms and spot a partial dependency in a real table.
**Say this in the interview:** "2NF removes partial dependency. In this table product_name depends only on product_id and customer_name only on order_id, both parts of the key, so I split it into products, orders and order_items."
**Answer:** **2NF (Second Normal Form) removes partial dependency.** 1NF: every cell holds one atomic (single) value and rows are unique. 2NF: 1NF plus no non-key column depends on only part of a composite key. 3NF: 2NF plus no non-key column depends on another non-key column (no transitive dependency).
**Step-by-step working:**
1. Key = (order_id, product_id). It is a composite key (made of two columns).
2. product_name is decided by product_id alone: a partial dependency. customer_name is decided by order_id alone: another partial dependency. So the table violates 2NF.
3. Fix: put each fact in the table whose key fully decides it: products(product_id, product_name), orders(order_id, customer_name), order_items(order_id, product_id).
4. Now every non-key column depends on the whole key of its table. There is no non-key to non-key dependency, so it is also in 3NF.
```sql
-- Run on Python sqlite3 with sample rows
CREATE TABLE products(product_id INT PRIMARY KEY, product_name TEXT);
CREATE TABLE orders(order_id INT PRIMARY KEY, customer_name TEXT);
CREATE TABLE order_items(order_id INT, product_id INT, PRIMARY KEY(order_id, product_id));
-- filled from the flat table: orders 1 (Asha, Laptop+Mouse) and 2 (Ravi, Laptop)
SELECT o.order_id, o.customer_name, p.product_name
FROM order_items i JOIN orders o USING(order_id) JOIN products p USING(product_id)
ORDER BY 1, 3;
```
```text
(1, 'Asha', 'Laptop')
(1, 'Asha', 'Mouse')
(2, 'Ravi', 'Laptop')
```
The join rebuilds the original data, and "Laptop" and each customer are now stored once.
**Check:** verified by script (the join returns the original three rows).
**Explain simply:**
- Normalisation means splitting a table so each fact is stored once, which prevents update mistakes (changing a product name in one row but not another).
- Partial dependency only matters when the key has more than one column.
- Transitive dependency example for 3NF: emp_id -> dept_id -> dept_name; move dept_name to a departments table.
**Likely follow-ups:** 1) *Is a table with a single-column key automatically in 2NF?* Yes, if it is in 1NF, because partial dependency needs a composite key. 2) *What is BCNF?* A stricter 3NF: every determinant must be a candidate key.
**Common mistakes / traps:** Choosing 3NF or 1NF as the answer (partial dependency is 2NF); calling product_name dependent on the "whole" key.

### Q27 ⭐⭐ 🟡 What does ACID stand for in databases? Give a one-line banking example for each property.
**Asked at:** commonly asked (no company-specific report found); DBMS basics are reported in some Accenture and Tiger Analytics tests (disputed, unverified).
**What the interviewer is checking:** Whether you know the four transaction guarantees.
**Say this in the interview:** "ACID is Atomicity, Consistency, Isolation, Durability: a transaction is all or nothing, keeps rules valid, does not clash with others, and survives a crash once committed."
**Answer:** **Atomicity, Consistency, Isolation, Durability.**
**Step-by-step working (banking: transfer 200 from A to B):**
1. Atomicity: both the debit and the credit happen, or neither does (no money lost halfway).
2. Consistency: rules stay true; the total money stays the same and a balance cannot go below zero if forbidden.
3. Isolation: two transfers at the same time do not see each other's half-finished work.
4. Durability: once the bank confirms, the transfer survives a power cut.
```sql
-- Python sqlite3: acct(name, bal) with CHECK(bal >= 0); A=500, B=100
UPDATE acct SET bal = bal - 800 WHERE name = 'A';   -- fails, then ROLLBACK
SELECT * FROM acct;
BEGIN; UPDATE acct SET bal = bal - 200 WHERE name='A';
       UPDATE acct SET bal = bal + 200 WHERE name='B'; COMMIT;
SELECT *, (SELECT SUM(bal) FROM acct) FROM acct;
```
```text
error: CHECK constraint failed: bal>=0
[('A', 500), ('B', 100)]
[('A', 300), ('B', 300)]   total 600
```
The bad update leaves nothing behind; the good transfer keeps the total at 600.
**Check:** verified by script.
**Explain simply:** A transaction is a bundle of steps treated as one unit; ACID makes the bundle trustworthy.
**Likely follow-ups:** 1) *Which property does a rollback support?* Atomicity. 2) *Which does a write-ahead log support?* Durability.
**Common mistakes / traps:** Writing "Accuracy" or "Concurrency" for A and C.
