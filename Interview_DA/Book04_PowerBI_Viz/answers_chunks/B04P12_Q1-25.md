### Q4 ⭐⭐⭐ 🟡 Which Power BI topic did you find hardest (Power Query, data modelling or DAX), and how did you overcome it?
**Asked at:** commonly asked (no company-specific report found). A Coursera Power BI interview guide (updated Dec 2025 per the sources file) lists project and data-model questions, but no learning-journey question.
**What the interviewer is checking:** Honest reflection and a real learning method.
**Say this in the interview:** "DAX, specifically filter context: the same measure gives different answers in different visuals. I overcame it by writing small measures on a nine-row table, predicting the result by hand, then checking in Power BI. Once I could predict the answers, CALCULATE made sense."
**Explain simply:**
- **Filter context** = the filters active where a measure is evaluated (slicers, rows, columns of the visual). It is why a total row can differ from the rows above it.
- Method: shrink the data, predict, check, then scale up (Q13).
- Pick one topic and be specific; "everything was hard" says nothing.
**Example:** Share of payroll by department. Plain `SUM` per row gives the dept's payroll; dividing by the grand total needs `ALL`, which removes the dept filter.
**Sample data:** Table `Employees` (9 rows, made up; Salary per month):

| EmpID | Dept | JoinDate | ExitDate | Salary |
|---|---|---|---|---|
| E001 | Sales | 2022-03-01 | | 40000 |
| E002 | Sales | 2021-06-15 | 2025-02-10 | 38000 |
| E003 | HR | 2020-01-10 | | 45000 |
| E004 | HR | 2023-04-01 | 2024-08-20 | 36000 |
| E005 | IT | 2019-09-01 | | 70000 |
| E006 | IT | 2022-11-01 | 2025-05-05 | 65000 |
| E007 | IT | 2024-02-01 | | 60000 |
| E008 | Sales | 2024-07-01 | | 35000 |
| E009 | HR | 2025-03-01 | | 42000 |

**DAX / Steps:** Not run here (no Power BI or DAX engine available).
```dax
Total Payroll = SUM ( Employees[Salary] )
Payroll Share =
DIVIDE ( [Total Payroll], CALCULATE ( [Total Payroll], ALL ( Employees[Dept] ) ) )
```
**Alternative:** `ALLSELECTED ( Employees[Dept] )` in place of `ALL` makes the share relative to what the user has selected in slicers.
**Result:** Reproduced with pandas (not produced by a DAX engine): HR 123,000 (28.5%), IT 195,000 (45.2%), Sales 113,000 (26.2%); grand total 431,000.
**Pandas check:**
```python
t = emp.groupby("Dept").Salary.sum(); print(t); print((t/t.sum()).round(3))
```
Output: `HR 123000, IT 195000, Sales 113000` and `HR 0.285, IT 0.452, Sales 0.262`.
**Version / licensing note:** DAX syntax from memory, unverified against Microsoft Learn (unreachable here).
**Edge cases:** DIVIDE returns blank on divide-by-zero; `ALL` ignores slicers on that column.
**Likely follow-ups:**
- *Filter context vs row context?* Row context = "this one row" (calculated columns, iterators like SUMX).
- *How would you get better?* More small drills (Q17).
**Common mistakes:** Saying "DAX is easy"; memorising formulas without understanding context; blaming the tool.

### Q6 ⭐⭐ 🟢 You already know Excel. What carried over to Power BI, and what did you have to unlearn?
**Asked at:** commonly asked (no company-specific report found).
**What the interviewer is checking:** Whether you understand the shift from cell-by-cell to table-and-filter thinking.
**Say this in the interview:** "Carried over: filtering logic, SUMIFS thinking, pivot-table thinking and many formula names. I had to unlearn cell references and copying formulas down. In Power BI you write a measure once and the filters decide the answer."
**Explain simply:**
- Carried over: pivot tables = matrix visual; SUMIFS = `CALCULATE ( SUM(...), filter )`; Power Query is the same engine as Excel's Get & Transform.
- Unlearn: no A1 cell references; no hand-typed totals; one table per topic, linked by relationships, instead of one giant sheet and VLOOKUPs.
- A **measure** is a formula calculated at display time for whatever filters are active.
**Example:** Excel: `=SUMIFS(C:C, A:A, "Sales", D:D, "")` for payroll of active Sales staff. Power BI: one measure used in every visual.
**Sample data:** use the `Employees` table in Q4.
**DAX / Steps:** Not run here.
```dax
Active Sales Payroll =
CALCULATE ( SUM ( Employees[Salary] ), Employees[Dept] = "Sales", ISBLANK ( Employees[ExitDate] ) )
```
**Alternative:** `FILTER ( Employees, Employees[Dept] = "Sales" && ISBLANK ( Employees[ExitDate] ) )` as the filter argument; more flexible but slower to read.
**Result:** Reproduced with pandas: all Sales payroll 113,000; active-only Sales payroll 75,000 (E001 40,000 + E008 35,000).
**Pandas check:**
```python
act = emp[emp.ExitDate.isna()]; print(emp[emp.Dept=="Sales"].Salary.sum(), act[act.Dept=="Sales"].Salary.sum())
```
Output: `113000 75000`.
**Version / licensing note:** DAX from memory, unverified (Learn unreachable).
**Edge cases:** Blank ExitDate means still employed; a blank in Excel can be "" text, in Power BI it is a true blank.
**Likely follow-ups:**
- *Why not just use Excel?* Bigger data, reusable model, scheduled refresh.
- *Is Power Pivot the same?* Same engine and DAX, inside Excel.
**Common mistakes:** Treating Power BI as "Excel with charts"; building one flat table with merged cells; avoiding measures.

### Q12 ⭐⭐ 🟡 How do you check that the numbers in your Power BI report are correct when there is no answer key?
**Asked at:** commonly asked (no company-specific report found).
**What the interviewer is checking:** Whether you validate rather than trust.
**Say this in the interview:** "I reconcile three ways: against the source file, against an independent calculation in Excel or pandas on a small slice, and against a sanity check, such as department figures adding up to the total. I also check blanks, duplicates and date boundaries."
**Explain simply:**
- Reconcile totals to source row counts and sums.
- Rebuild one number by hand for one department and one month.
- Check that parts add to the whole; percentages do not add, so recompute them from counts.
- Test boundary dates (people leaving on 31 Dec).
**Example:** Attrition 2025 on the Q4 `Employees` table: leavers = 2, opening headcount 7, closing 6, average 6.5, attrition 30.8%. Note E004 left in 2024 and E009 joined in 2025; neither is a 2025 leaver or opening employee.
**Sample data:** `Employees` table in Q4.
**DAX / Steps:** Not run here.
```dax
Leavers 2025 = CALCULATE ( COUNTROWS ( Employees ), Employees[ExitYear] = 2025 )
Attrition % = DIVIDE ( [Leavers 2025], AVERAGE headcount )  -- see note
```
Use real measures for opening and closing headcount (`Opening HC`, `Closing HC`), then `Attrition % = DIVIDE ( [Leavers 2025], ( [Opening HC] + [Closing HC] ) / 2 )`. `ExitYear` is a helper column assumed to exist (`YEAR ( Employees[ExitDate] )`).
**Alternative:** Put the same data in a Power BI table visual with row details and compare to an Excel pivot.
**Result:** Reproduced with pandas: overall Start 7, End 6, Leavers 2, Attrition 0.308. By department: HR 0 leavers (rate 0.0), IT 1 (0.4), Sales 1 (0.4). Parts check: dept leavers sum 2, starts sum 7, ends sum 6; but the average of department rates is 0.267, not 0.308, so rates must be recomputed, not averaged.
**Pandas check:**
```python
print(tot); print(bd); print(round(bd.Attr.mean(),3), tot.Attr)
```
Output: `Start 7.0, End 6.0, Leavers 2.0, AvgHC 6.5, Attr 0.308`; `0.267 0.308`.
**Version / licensing note:** DAX from memory, unverified. In the Service you can also use "Analyze in Excel"; availability and licence from memory, unverified.
**Edge cases:** Blank exit dates, duplicate employee IDs, many-to-many relationships, time zones on timestamps, totals vs sum of rows.
**Likely follow-ups:**
- *Why doesn't the total equal the sum of rows?* Rates and distinct counts are not additive.
- *What if the source is wrong?* Flag it to the data owner.
**Common mistakes:** Trusting the first output; averaging percentages; not checking date boundaries.

**DAX / Steps:** Not run here.

```dax
Present Days = CALCULATE ( COUNTROWS ( Attendance ), Attendance[Status] = "Present" )
Employees Present = CALCULATE ( DISTINCTCOUNT ( Attendance[EmpID] ), Attendance[Status] = "Present" )
```
**Alternative:** Learn by testing in DAX query view or a calculated table; availability and licensing from memory, unverified.

```python
p = att[att.Status=="Present"]; print(len(p), p.EmpID.nunique())
```

Output: `6 3`.
**Version / licensing note:** Not verified (Learn unreachable here); from memory, unverified. Always check the page's "applies to" notes.
