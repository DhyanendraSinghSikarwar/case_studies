## Sources read
| Topic | URL | Facts taken |
|---|---|---|
| Isolation levels | https://www.postgresql.org/docs/current/transaction-iso.html | Standard table: Read Uncommitted allows dirty/nonrepeatable/phantom; Read Committed blocks dirty only; Repeatable Read blocks dirty + nonrepeatable (phantom allowed by the standard); Serializable blocks all. PostgreSQL treats Read Uncommitted as Read Committed (no dirty reads ever); default is Read Committed; its Repeatable Read is snapshot isolation and also prevents phantoms; Serializable failures raise SQLSTATE 40001 and the app must retry. |
| Recursive CTE, cycles | https://www.postgresql.org/docs/current/queries-with.html | Form: non-recursive term, UNION [ALL], recursive term. Evaluated iteratively with a working table. UNION removes duplicates, UNION ALL keeps all. Cycle handling: carry a `path` array and test `id = ANY(path)`, or the built-in `CYCLE id SET is_cycle USING path`. Changing UNION ALL to UNION does NOT stop a loop when a depth column makes rows distinct. A recursive term that never returns zero rows loops forever; `LIMIT` in the outer query works in PostgreSQL only as a trick (not recommended in production). `SEARCH DEPTH/BREADTH FIRST` orders the output. |
| Multi-column index | https://www.postgresql.org/docs/current/indexes-multicolumn.html | B-tree is best with constraints on the leftmost columns: equality on leading columns plus one inequality on the next column narrow the scan; conditions on later columns are checked inside the index. `WHERE minor = 2` alone on index (major, minor) is usually inefficient (PostgreSQL 18 added skip scan, used only when the leading column has few distinct values). Docs advise multicolumn indexes sparingly; >3 columns rarely helpful. |
| Index-only / covering | https://www.postgresql.org/docs/current/indexes-index-only-scans.html | Index-only scan needs the index type to support it (B-tree always) and the query to reference only indexed columns. Visibility map caveat: if the heap page is not marked all-visible, the heap is still visited. `CREATE INDEX tab_x_y ON tab (x) INCLUDE (y);` makes a covering index; included columns bloat the index, so be conservative. |
| Partitioning | https://www.postgresql.org/docs/current/ddl-partitioning.html | Benefit is normally worthwhile only when the table would otherwise be very large (rule of thumb: bigger than server memory). Range / list / hash methods. Partition pruning skips partitions that cannot match the WHERE clause (`enable_partition_pruning` default on). Dropping/detaching an old partition is far faster than bulk DELETE and avoids VACUUM overhead. |
| EXPLAIN | https://www.postgresql.org/docs/current/using-explain.html | `cost=startup..total` in arbitrary units (not ms); `rows` = estimated rows emitted; Seq Scan vs Index Scan vs Bitmap Index/Heap Scan (moderate selectivity). `Index Cond:` applied via the index, `Filter:` checked row by row. `EXPLAIN ANALYZE` actually EXECUTES the statement (wrap INSERT/UPDATE/DELETE in BEGIN ... ROLLBACK); adds `actual time` in ms, real rows, loops (values are per-loop averages), Rows Removed by Filter. Big estimate-vs-actual mismatch usually means stale statistics (run ANALYZE). |
| MySQL indexes | https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html | Most indexes are B-trees; leftmost-prefix rule for multi-column indexes; covering index answers from the index alone; small tables or queries reading most rows can be faster with a full scan. The page does NOT cover InnoDB clustered indexes: "PK is the clustered index; secondary indexes store the PK" is from general knowledge (label "from memory"). |
| Kimball techniques | https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/ | Only the list of names was readable: SCD Type 0 Retain original, Type 1 Overwrite, Type 2 Add new row, Type 3 Add new attribute, Type 4 Add mini-dimension, Type 6 Add Type 1 attributes to Type 2 dimension. Definitions of grain/fact/dimension were NOT on the page: write them as standard textbook definitions, labelled "from memory". |
| Cohort / sessionization patterns | web search 2026-10-21 (prachub.com/resources/sql-for-data-analysis, dataford.io/interview-guides/questions/structure-retention-cohort-analysis, datadriven.io gaps-and-islands lessons) | Snippets only, not fetched. Patterns: sessionization = LAG -> CASE flag -> running SUM; consecutive days = ROW_NUMBER difference trick; for thresholds such as 30 minutes the row-number trick does not apply, use LAG + running SUM. Confirm whether the boundary is "> 30" or ">= 30" minutes. Immature (recent) cohorts are a common correctness pitfall. Study material, not confirmed interview content. |
